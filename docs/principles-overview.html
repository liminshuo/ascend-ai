AI 亲和原则

为什么要做 AI 亲和原则

当用户通过大模型检索产品与技术问题，答案往往依赖文档站、官网等公开内容能否被机器稳定发现、完整读取并正确理解。若入口不可达、正文抓不全，或版本与语义含混，模型更容易用训练记忆填补缺口，表现为幻觉、答非所问或过时指引，直接损害知识交付效率与产品体验。

AI 亲和原则据此将答问链路拆解为可达、可读、可理解、可操作、可验证五层能力目标，为设计、内容与前端提供统一对照标准，使同一套公开面既服务读者，也可被生成式检索与知识入库可靠消费。

G1. 确保文档与官网的关键入口可被机器发现并进入

可达原则关注「找不找得到」。生成式检索与知识入库的前提，是公开面（文档站、官网知识页等）对爬虫与模型可见、可进入：有稳定入口、不被 robots 误挡。站内层级与章节位置也应可被定位（见 G1.2）。达不到本原则，后续可读、可理解均无从谈起。

答问阶段

发现候选页。用户提问后，模型需要检索并找到可引用的官方页面（文档或官网）。本原则决定这些页面能否被稳定发现并进入候选与引用池。

益处

官方事实页能进入候选与引用池，降低答非所问、只命中壳页或营销页；为后续抓取与消歧提供可靠入口。

注意事项

营销 / 活动页可不做完整亲和改造，但要在收录策略里划清范围；勿用不稳定短链或登录墙挡住官方事实页；已持有 URL 时入口仍须真实可进入；双轨必须同源，禁止给人一套、给机器另一套内容。

G1.1 发现入口与索引通畅

如何做

  • 部署并维护 llms.txt / sitemap，构建管道随发布更新。
  • robots 放行可索引与 source 路径；URL 稳定、可引用。
  • 覆盖文档站与官网等需被引用的公开面。

G1.2 站内位置可定位

如何做

  • 提供面包屑，标明当前页在站点层级中的位置。
  • 提供邻篇导航，便于沿手册结构继续发现。
  • 章节使用稳定锚点，支持定位到具体小节。

G1.3 双轨同源可消费

如何做

  • 在 HTML 之外提供平行 MD / source 等结构化纯文本源。
  • 机器源与人读页同源更新，非按 UA 动态换皮。
  • 页面模板可声明机器源 / alternate 入口，便于发现。

G2. 确保机器可完整读取正文，并将非文本与隐藏态内容等价入库

可读原则关注「读不读得到」。入口找到之后，正文、图意、表格、代码以及 Tab / 折叠等默认隐藏内容，必须以可抓取文本进入知识层。本阶段是 GEO 亲和改造的主战场：页面「看起来有内容」不等于机器「拿到了可引用的 chunk」。

答问阶段

打开页面、读取正文。模型选定 URL 后抓取页面内容。本原则决定抓到的是完整可引用文本，还是空壳、缺图意、缺 Tab / 折叠中的关键信息。

益处

回答能引用完整步骤与结论；减少空壳页、半页入库、只抓到激活 Tab 导致的空泛复述。

注意事项

装饰性图片可不强转写，但信息型图必须有字；勿把关键步骤只放在悬停 / 蒙版里；代码勿混入行号等噪声；「看起来全」不等于「DOM 里全」——以禁 JS 抓取为准。

G2.1 正文在 HTML 中完整可得

如何做

  • 正文 SSR / 首包输出完整，关键段落不依赖纯客户端渲染。
  • 避免无限滚动、虚拟列表导致主体内容不在 DOM。
  • 发布前可用禁 JS 抓取做完整性对照。

G2.2 图、表、代码文本化转写

如何做

  • 信息型图提供 alt / 图注或正文转写；结构图优先可机读源。
  • 表格用语义化结构，结论可读、可切 chunk。
  • 代码块保持干净可复制，避免行号等噪声入库。

G2.3 隐藏块不漏抓

如何做

  • Tab、折叠等内容默认全量进入 DOM，或经 SSR 完整输出。
  • 关键步骤不仅挂在悬停或蒙版交互上。
  • 控件与状态配备可抓取的独立标签 / 文案。

G3. 确保机器可消歧文档结构、生命周期与语义指称

可理解原则关注「读得对不对」。内容入库后仍可能切错章节、混用版本、误读状态与链接含义。本原则要求结构、时效与语义指称对机器同样明确，使召回与引用落在正确范围，而不是「有字但答偏」。

答问阶段

整理证据、判断是否够用。模型汇总已读内容，决定能否作答或需否继续检索。本原则影响版本是否选对、章节是否切准、状态与链接是否被误读。

益处

降低错误引用与过时答案；召回落在正确章节与版本，回答更可核对、可信。

注意事项

避免「最新版」等模糊措辞；弃用内容须显式标注，不能只靠视觉灰色；勿用连续空标签撑间距破坏结构感知；标题层级服务于篇章结构，不替代术语表类的词义定义。

G3.1 标题层级与主次清晰

如何做

  • H1–H6 真实反映篇章结构，利于知识树与 chunk 边界。
  • 推荐、相关阅读等噪声置后，不抢主文。
  • 用语义结构 + CSS 控制间距，避免无语义空标签撑版。

G3.2 版本、时效、废弃可区分

如何做

  • 外显产品 / 文档版本号，避免「最新版」式模糊说法。
  • 提供可机读的更新日期（如 time datetime / 元数据）。
  • 弃用、失效内容显式标注，并给出替代入口。

G3.3 链接与状态语义明确

如何做

  • 链接锚文本写清指向（参考文档、下载、外链等）。
  • 状态词完整可辨（进行中、已完结、可选 / 必选等）。
  • 警示级别用语义化结构表达，不仅靠颜色区分。

G4. 确保操作类内容可被拆解执行，示例可落地到可运行路径

可操作原则关注「能不能照着做」。面向安装、调用、配置等任务时，亲和文档应把步骤写成可执行单元，并尽可能提供可复制示例与在线尝试入口，使模型输出的操作指引可落地，而不是停留在抽象叙述。

答问阶段

组织可执行回答。证据足够后，模型给出步骤或示例。本原则决定回答能否落到可照做的路径。

益处

人机都能沿同一路径完成任务，缩短试错；减少「说了等于没说」的抽象指引。

注意事项

示例须与当前版本一致；Playground 为增强项，不能替代正文步骤；嵌入式沙箱需有 SSR / 静态降级，避免机器抓不到代码文本；不要求大模型自行进入沙箱完成验证。

G4.1 示例路径可参照

如何做

  • 给出可复制的标准示例（命令、请求、关键参数）。
  • 示例与当前文档版本对齐，随发布更新。
  • 说明适用场景与前置条件，避免误套。

G4.2 提供在线尝试入口

如何做

  • 在合适处提供 Playground / 在线尝试链接，文案明确。
  • 尽量支持预填示例，减少空白环境。
  • 概念说明页可不强制；操作类页面优先考虑。

G4.3 步骤可按序执行

如何做

  • 步骤写清对象与动作，拆成可按序执行的最小单元。
  • 使用有序列表等结构化表达，避免散文式步骤。
  • 必要时标明可选步骤与分支条件。

G5. 确保执行结果可对照核验，空态与异常具备可处理说明

可验证原则关注「做完能不能核对」。任务型内容应给出预期结果、验证方式，以及空数据、失败时的处理说明，形成闭环。缺少本原则时，模型容易在结果不明或异常场景下臆造结论。

答问阶段

核对结果与收口作答。模型依据证据给出最终结论。本原则提供预期结果与异常说明，支撑可靠核对。

益处

人与模型都能核对「是否做对」；异常有官方说法，减少幻觉与无效重试。

注意事项

预期结果须可观察、可复现，避免主观形容词；空态文案不能只有图标无字；验证说明应贴近真实环境，勿写已失效的检查命令。

G5.1 提供验证区块或用例

如何做

  • 设置独立的验证 / 检查章节或用例。
  • 给出可对照的输入与输出。
  • 操作类、排障类页面优先配置。

G5.2 写明预期结果

如何做

  • 写明命令输出、界面变化、状态标志等可见判据。
  • 判据可复现，避免「运行正常」等主观表述。
  • 与步骤中的动作一一对应，便于核对。

G5.3 空态与异常可处理

如何做

  • 无数据、失败时写清含义与下一步。
  • 空态使用可抓取文案，不只依赖图标。
  • 常见异常给出官方处理路径，减少臆造。
