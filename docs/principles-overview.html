AI 亲和原则

为什么要做 AI 亲和原则

当用户通过大模型检索产品与技术问题，答案往往依赖文档站、官网等公开内容能否被机器稳定发现、完整读取并正确理解。若入口不可达、正文抓不全，或版本与语义含混，模型更容易用训练记忆填补缺口，表现为幻觉、答非所问或过时指引，直接损害知识交付效率与产品体验。

AI 亲和原则据此将答问链路拆解为可达、可读、可理解、可操作、可验证五层能力目标，为设计、内容与前端提供统一对照标准，使同一套公开面既服务读者，也可被生成式检索与知识入库可靠消费。概念边界与适用范围见 设计背景。

G1. 可达 · 确保文档与官网的关键入口可被机器发现并进入

核心原则

聚焦于「找不找得到」。这是生成式检索与知识入库的前置条件。公开面（文档站、官网知识页）必须对爬虫与大模型完全可见、可进入：有稳定入口、不被 robots 误挡，站内层级与章节位置可被精准定位。

模型行为阶段（检索发现阶段）

在基于用户提问的检索初筛中，模型需要快速定位并发现可引用的官方事实页。本原则决定了这些页面能否稳定进入候选池与引用池。

核心益处

确保官方事实页优先进入候选池，降低模型答非所问或仅命中壳页、营销页的风险；为后续的“抓取”与“消歧”提供可靠的入口基础。

注意事项

  • 范围划定：营销/活动页可不做完整亲和改造，但须在收录策略中明确划清界限。
  • 入口真实：避免使用不稳定短链或登录墙阻挡官方事实页；即便已持有 URL，入口也必须真实可进入。
  • 双轨同源：人读 HTML 与 MD / source 须同源同步，严禁按 UA 换皮；入口与平行源基建归在可达（见 G1.2 / G1.3）。

G1.1 发现入口与索引通畅

核心目的

打通基础入口层，解决“机器能不能找得到”的问题。通过标准协议与基建，确保爬虫与大模型能稳定进入应被引用的公开页。

执行要点

  • 持续部署并维护 llms.txt / sitemap，建立随发布自动更新的构建管道。
  • 配置 robots 放行可索引与 source / Markdown 路径；确保 URL 永久稳定、可被引用。
  • 全面覆盖文档站、官网及所有需要被引用的公开页面。

G1.2 渲染页入口可辨识

核心目的

解决“人读页上找不找得到机器入口”的问题。发现层部署之后，须在渲染页用可读文案标出站级 / 页级 / 内容块入口，禁止只靠图标或悬停。

执行要点

  • 页脚等次要区标出站级清单（如 llms.txt）；文档页头提供「复制 / 打开 Markdown」等页级入口。
  • 强视觉块可挂平行 MD 入口；文案自描述，与 source / llms 路径语义一致。
  • 入口须首包直出、默认可跟链；细则见「AI入口可识别」原则页与设计专项。

G1.3 双轨同源可消费

核心目的

打造机器消费轨道，解决“用什么方式最快、最好进”的问题。在 HTML 之外提供平行的 MD / source 源，声明 alternate，并保证与人读页同源更新，衔接到下一阶段的“可读”。

执行要点

  • 在 HTML 之外提供平行的 MD / source 等结构化纯文本源，作为“快车道”。
  • 机器源与人读页必须同源实时更新，严禁按 UA 动态换皮。
  • 页面模板需明确声明机器源 / alternate；版面如何标出入口见 G1.2。

G1.4 站内位置可定位

核心目的

建立精准定位机制，解决“机器找对地方没”的问题。通过建立知识树坐标，用面包屑标定层级、邻篇建立上下文、稳定锚点落到小节，使机器明确当前页面的准确位置。

执行要点

  • 提供标准面包屑，标明当前页在站点层级中的精确位置。
  • 提供邻篇导航，便于模型沿手册结构进行上下文连贯的发现。
  • 为所有章节使用稳定锚点，支持模型精准定位到具体小节。

G2. 可读 · 确保机器可完整读取正文，并将非文本与隐藏态内容等价入库

核心原则

聚焦于「读不读得到」。入口找到之后，正文、图意、表格、代码、音视频要点，以及 Tab / 折叠、悬停、蒙版、控件状态等默认不可见或未展开内容，必须以可抓取文本进入知识层。本阶段是亲和改造的主战场：页面「看起来有内容」不等于机器「拿到了可引用的 chunk」。

模型行为阶段（内容抓取阶段）

模型选定 URL 并进入页面读取正文的阶段。本原则直接决定了模型抓到的是完整可引用的文本，还是空壳、缺图意、缺音视频要点、缺关键步骤的半拉子内容。

核心益处

确保生成的回答能完整引用到具体的步骤与结论；大幅减少空壳页、半页入库，以及只抓到激活 Tab、漏掉控件标签或媒体要点导致的大模型空泛复述与信息缺失。

注意事项

  • 信息图必有字：装饰性图片可不强行转写，但信息型图表必须有可抓取的替代文案。
  • 媒体不独表意：音视频不得独自承载关键步骤与结论，须有可读取的文字要点伴随。
  • 交互不藏步骤：严禁把关键步骤只放在悬停、蒙版或点击触发里。
  • 代码去噪声：代码块入库前需剔除行号等无用噪声，保持纯净。
  • 以禁 JS 为准：开启 JS 时“看起来全”，不代表禁用 JS 后“DOM 里全”，必须以最严苛的抓取标准验证。

G2.1 正文在 HTML 中完整可得

核心目的

解决机器能否读到完整正文的问题，确保核心内容不因纯客户端渲染或虚拟列表导致主体缺失。

执行要点

  • 正文必须由 SSR / 首包完整输出，关键段落严禁依赖纯客户端渲染。
  • 避免使用无限滚动、虚拟列表等导致主体内容不在 DOM 中的交互方式。
  • 发布前必须使用禁 JS 抓取工具，进行完整性对照测试。

G2.2 图、表、代码与媒体文本化转写

核心目的

确立等价转写标准，解决“非文本内容进不了知识层”的问题。将图意、表格结论、代码逻辑、音视频要点以及图标/颜色所承载的语义，全量等价转化为可抓取、可切 chunk 的文本，使结论顺利进入引用池。

执行要点

  • 信息型图片提供 alt / 图注或正文转写；结构图优先提供可机读源文件（如 Mermaid、SVG 原文）。
  • 表格使用语义化结构（如 <th>），确保数据结论可读、可切 chunk。
  • 代码块保持干净可复制，代码逻辑必须无行号等噪声入库。
  • 音视频旁必须提供可读取的文字要点（关键步骤、参数、结论）；严禁让机器“听完 / 看完”才能答题。
  • 信息型图标、颜色语义须有对应文字说明；严禁颜色单独承载警示或状态含义。

G2.3 隐藏块与控件态不漏抓

核心目的

确立交互态等价抓取标准，解决“默认隐藏态与交互态漏抓”的问题。确保 Tab、折叠、悬停、蒙版中的关键内容，以及控件标签与数值，与可见正文拥有同等抓取地位，避免只抓到激活态或无字控件导致信息缺失。

执行要点

  • Tab、折叠等内容默认全量进入 DOM，或经 SSR 完整输出。
  • 关键步骤严禁只挂在悬停或蒙版交互上；蒙版严禁遮挡可抓取的关键说明。
  • 控件须配备可抓取的独立标签；关键数值、量程与状态必须有文字转写，严禁只靠无字图标或占位暗示。

G3. 可理解 · 确保机器可精准消歧文档结构、生命周期与语义指称

核心原则

聚焦于「读得对不对」。内容入库后仍可能切错章节、混用版本、误读状态与链接含义。本原则要求结构、时效与语义指称对机器同样明确，使召回与引用落在正确范围，而不是「有字但答偏」。

模型行为阶段（语义消歧与证据融合阶段）

在整理证据、判断是否够用的节点，模型汇总已读内容，决定能否作答或需否继续检索（对应流程图中的“汇总当前证据”与“判断证据是否充分”）。本原则直接决定版本是否选对、章节是否切准、状态与链接是否被误读。

核心益处

降低错误引用与过时答案的产出率；确保召回精准落在正确章节与版本，让最终回答更可核对、更可信。

注意事项

  • 措辞可核：避免「最新版」等模糊说法，版本须可指认。
  • 弃用显式：弃用内容须显式标注，不能只靠视觉灰色。
  • 结构真实：勿用连续空标签撑间距；标题层级服务篇章，不替代术语定义。

G3.1 标题层级与主次清晰

核心目的

确立清晰的知识树骨架，解决“篇章结构是否被切对”的问题。用真实标题层级与主次排版，让 chunk 边界清晰，避免噪声抢占主文。

执行要点

  • H1–H6 真实反映篇章结构，利于知识树与 chunk 边界。
  • 推荐、相关阅读等噪声置后，不抢主文。
  • 用语义结构 + CSS 控制间距，避免无语义空标签撑版。

G3.2 版本、时效、废弃可区分

核心目的

标定知识的生命周期，解决“版本与时效是否混用”的问题。使产品 / 文档版本、更新时间与弃用状态可机读区分，避免过时内容被当作现行事实引用。

执行要点

  • 外显产品 / 文档版本号，避免「最新版」式模糊说法。
  • 提供可机读的更新日期（如 time datetime / 元数据）。
  • 弃用、失效内容显式标注，并给出替代入口。

G3.3 链接与状态语义明确

核心目的

消除指向与状态的语义歧义，解决“链接与状态是否被误读”的问题。让链接指向、状态词与警示级别对机器同样明确，降低指称歧义。

执行要点

  • 链接锚文本写清指向（参考文档、下载、外链等）。
  • 状态词完整可辨（进行中、已完结、可选 / 必选等）。
  • 警示级别用语义化结构表达，不仅靠颜色区分。

G4. 可操作 · 确保操作类内容可被拆解执行，示例可落地至可运行路径

核心原则

聚焦于「能不能照着做」。面向安装、调用、配置等任务时，文档应把步骤写成可执行单元，并提供可复制示例与在线尝试入口，使模型输出的操作指引可落地，而非停留在抽象叙述。

模型行为阶段（执行与终答阶段）

在组织可执行回答阶段，证据足够后，模型给出步骤或示例。本原则决定回答能否落到可照做的路径。

核心益处

确保人机都能沿同一路径完成任务，缩短试错成本；有效减少「说了等于没说」的抽象指引。

注意事项

  • 示例对齐版本：示例须与当前文档版本一致，随发布更新。
  • Playground 不替代步骤：在线尝试为增强项，不能替代正文可执行步骤。
  • 沙箱可降级：嵌入式沙箱需有 SSR / 静态降级，避免机器抓不到代码文本；不要求大模型自行进入沙箱完成验证。

G4.1 示例路径可参照

核心目的

确立明确的标准路径，解决“有没有可照抄路径”的示例问题。提供与当前版本对齐的可复制标准示例，并写清适用场景与前置条件。

执行要点

  • 给出可复制的标准示例（命令、请求、关键参数）。
  • 示例与当前文档版本严格对齐，随发布更新。
  • 说明适用场景与前置条件，避免误套。

G4.2 提供在线尝试入口

核心目的

降低环境搭建门槛，解决“能否更快上手试跑”的入口问题。在合适页面提供明确的在线尝试入口，并尽量预填示例，降低空白环境成本。

执行要点

  • 在合适处提供 Playground / 在线尝试链接，文案明确。
  • 尽量支持预填示例，减少空白环境。
  • 概念说明页可不强制；操作类页面优先考虑。

G4.3 步骤可按序执行

核心目的

规范化操作指引，解决“步骤能否拆成可执行单元”的编排问题。把操作写成可按序执行的最小单元，并标明可选步骤与分支条件。

执行要点

  • 步骤写清对象与动作，拆成可按序执行的最小单元。
  • 使用有序列表等结构化表达，避免散文式步骤。
  • 必要时标明可选步骤与分支条件。

G5. 可验证 · 确保执行结果可对照核验，空态与异常具备可处理说明

核心原则

聚焦于「做完能不能核对」。任务型内容需给出预期结果、验证方式，以及空数据、失败时的处理说明，形成完整闭环。缺少本原则，模型极易在结果不明或异常场景下臆造结论，导致幻觉产生。

模型行为阶段（事实核查与终答阶段）

在核对结果与收口作答阶段，模型依据证据给出最终结论。本原则提供预期结果与异常说明，支撑可靠核对。

核心益处

确保人与模型都能客观核对「是否做对」；异常情况有官方处理口径，有效遏制幻觉与无效重试，极大提升最终回答的综合置信度。

注意事项

  • 杜绝臆造：严禁在结果不明或异常场景下凭空猜测结论。
  • 显式处理：空态与异常处理说明必须显式标注，不能只靠视觉提示（如置灰）暗示。
  • 闭环收口：预期结果必须能对应执行步骤，若无明确预期，需明确告知无法验证。

G5.1 提供验证区块或用例

核心目的

确立闭环验证机制，解决“有没有对照核验入口”的问题。设置独立的验证 / 检查章节或用例，给出可对照的输入与输出。

执行要点

  • 设置独立的验证 / 检查章节或用例。
  • 给出可对照的输入与输出。
  • 操作类、排障类页面优先配置。

G5.2 写明预期结果

核心目的

确立清晰判据标准，解决“怎样算做对了”的问题。写明可观察、可复现的预期结果，并与步骤动作一一对应。

执行要点

  • 写明命令输出、界面变化、状态标志等可见判据。
  • 判据可复现，严禁使用「运行正常」等主观表述。
  • 与步骤中的动作一一对应，便于核对。

G5.3 空态与异常可处理

核心目的

确立异常收口路径，解决“异常时该怎么办”的问题。为空数据与失败场景提供可抓取说明与官方处理路径，减少臆造。

执行要点

  • 无数据、失败时写清含义与下一步。
  • 空态使用可抓取文案，不依赖纯图标展示。
  • 常见异常给出官方处理路径，杜绝凭空臆造。
