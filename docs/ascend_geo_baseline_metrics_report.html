GEO MEASUREMENT FRAMEWORK · 2026-10-19

昇腾社区 GEO 基线指标体系与复测方案

本报告将 GEO 评估从“基础设施检查”升级为“效果指标 + 原因指标”双层体系。用于记录优化前的真实基线、定位问题，并在优化后使用同一问题集、同一平台和同一统计口径复测。

版本：V1.0对象：昇腾社区用途：优化前基线 / 优化后复测
先看结论

报告应回答的 3 个问题

  1. AI 表现怎么样：回答昇腾相关问题时，AI 是否能找到、提及并引用昇腾社区内容，是否准确理解信息。
  2. 问题出在哪里：网站是否可抓取、页面是否可索引、标题和正文是否清晰、引用材料是否可访问。
  3. 优化是否有效：同一套问题、平台、轮次和评分规则复测，计算百分点变化和相对提升率。

重要：现有 robots.txt、Sitemap 和 llms.txt 文件只能支持部分技术与内容清单统计，不能直接推导 AI 答案引用率、品牌提及率或事实准确率。下表会明确标记哪些已测、哪些必须通过新一轮测试建立基线；未测指标不填猜测值。

03

建议采用的 GEO 核心 KPI

建议把以下 6 项作为管理层最常看的效果指标；其他技术指标用于解释原因。每次复测都要记录分子、分母和原始样本，避免只报一个百分比。

指标定义 / 计算公式它回答什么当前状态
1. 来源发现率回答中出现昇腾社区官方来源的有效测试数 ÷ 有效测试总数 × 100%AI 能否发现并把昇腾社区识别为相关来源？待实测
2. 答案引用率最终答案明确引用 / 链接到昇腾社区内容的测试数 ÷ 有效测试总数 × 100%AI 是否真正把社区内容用于回答，而不只是提到品牌？待实测
3. 品牌提及率回答中提及“昇腾 / Ascend / 昇腾社区”等目标实体的测试数 ÷ 有效测试总数 × 100%在相关问题中品牌是否进入答案？待实测
4. 引用支持率经核验、来源确实支持其所对应主张的引用数 ÷ 抽检引用总数 × 100%AI 引用了来源之后，引用是否真的能支撑答案？待实测
5. 事实准确率经核验正确的事实项数 ÷ 被核验事实项总数 × 100%产品名称、能力、适用场景、版本、参数等信息是否准确？待实测
6. 关键问题覆盖率回答完整覆盖预先定义的关键答案要点的测试数 ÷ 有效测试总数 × 100%答案是否包含用户真正需要的信息，而不只是泛泛提及？待实测
口径区别：“品牌提及”不等于“来源发现”；“来源发现”不等于“答案引用”；“答案引用”也不等于“引用支持”。这几个指标必须分开统计，否则无法判断优化究竟改善了哪一环。

05

AI 回答测试：建议固定 40 道问题

为保证优化前后可比较，建议建立 8 类 × 每类 5 道 = 40 道固定问题。问题应覆盖用户真实需求，而不是只用品牌词直接询问“昇腾是什么”。

问题类别数量示例方向（示例需在正式测试集里固定措辞）主要观察点
品牌 / 平台认知5昇腾社区提供什么资源？适合哪些开发者？品牌提及、官方来源发现、核心定位准确性
产品与硬件5某类昇腾硬件的用途、能力或适用场景是什么？产品事实准确率、官方产品页引用
软件栈与工具5CANN、MindStudio 等工具分别解决什么问题？术语理解、内容覆盖、官方文档引用
开发入门 / 教程5如何开始部署或运行一个昇腾开发任务？步骤完整度、教程发现率、链接有效性
故障排查 / 错误码5遇到某个错误码或常见故障应如何定位？错误码准确性、证据支持率、答案可操作性
兼容性 / 版本5某软件版本与硬件 / 驱动是否兼容？版本准确率、日期 / 版本信息、引用时效性
行业方案 / 使用场景5昇腾如何支持某类模型或行业应用？场景匹配度、官方案例发现率、关键要点覆盖

测试规模建议：固定 40 道问题，选择 3 个目标 AI 平台，每道问题每个平台重复测试 2 次，合计 240 个回答样本。若资源有限，可先用 1 个平台建立试运行基线，但不要把单次回答当作稳定结论。测试平台、模型版本、联网 / 搜索开关、日期、问题原文均需记录。
06

如何计算优化提升率

百分点变化（优先展示）

复测值 − 基线值

例如引用率从 20% 提升到 30%，变化为 +10 个百分点。

相对提升率

(复测值 − 基线值) ÷ 基线值 × 100%

同一例子相对提升率为 +50%。当基线为 0 时，相对提升率不适用，应报告百分点变化和实际计数。

推荐每次复测报告同时展示：基线值、复测值、百分点变化、相对提升率、分子 / 分母、样本数、平台和日期。

指标基线示例（仅演示）复测示例（仅演示）百分点变化相对提升率
答案引用率20%（8/40）30%（12/40）+10 个百分点+50%
事实准确率80%（40/50）90%（45/50）+10 个百分点+12.5%

上表仅展示计算方法，不是昇腾社区的实际测试结果。正式报告必须用实测数据替换。

07

复测必须控制的条件

  • 问题集固定：优化前后使用同一批问题和完全一致的措辞，不随意替换为更容易触发品牌的问法。
  • 平台和设置固定：记录平台、模型版本、联网 / 搜索状态、语言、测试日期与重复次数。
  • 判分规则固定：提前定义何为品牌提及、官方来源、有效引用、事实正确和要点覆盖；尽可能由同一规则或双人复核。
  • 保留原始证据：保存完整回答、引用链接、页面内容、截图或导出记录，不能只保留最终分数。
  • 按问题类别拆分：整体分数提升可能掩盖某一类问题下降，应同时报告类别级结果和平台级结果。
  • 技术与效果分开：页面可抓取率提高是原因指标，不代表 AI 引用率必然同步提高；需要分别测量。
08

建议交付的基线数据表

每次测试建议维护两张明细表和一张汇总表：

A. AI 回答样本表

  • 问题 ID、类别、问题原文
  • 平台 / 模型 / 测试时间 / 重复序号
  • 回答全文、是否提及品牌
  • 是否出现官方来源、是否引用社区
  • 引用 URL、引用是否支持主张
  • 事实正确项、缺失要点、人工评分

B. 页面技术样本表

  • URL、页面类型、语言
  • HTTP 状态、最终 URL、重定向
  • robots / noindex / canonical
  • Title、H1、description、正文可读性
  • llms.txt 链接状态与内容匹配情况
  • 问题级别、整改动作、复测结果

C. 管理层汇总表

每个 KPI 一行：基线值｜本次值｜变化百分点｜相对提升率｜样本数｜主要问题｜已完成整改｜下一步动作。另按平台、问题类别和页面类型拆分。

09

执行顺序与本轮报告的定位

  1. 先冻结指标定义和问题集：确定 40 道测试问题、目标 AI 平台及判分规则。
  2. 采集 AI 表现基线：完成第一轮回答测试，生成来源发现率、答案引用率、品牌提及率、引用支持率、事实准确率和关键问题覆盖率。
  3. 并行做技术抽样：对 Sitemap URL、重点页面和 llms.txt Markdown 链接开展 HTTP / 索引信号检查。
  4. 按证据排优先级整改：把技术问题和内容问题映射到相应 KPI，不以配置项数量代替效果。
  5. 同口径复测：使用同样的问题集和平台条件，报告百分点变化、相对提升率和样本数。
最终原则：GEO 基线不是一份静态“问题清单”，而是一套可复测的测量系统。当前已有的 Sitemap 数值作为技术基线的一部分保留；AI 可见度与引用表现需要通过固定问题集实测后建立，不能从配置文件推算。
