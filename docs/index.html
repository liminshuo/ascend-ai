研究主题

昇腾社区 AI 亲和原则

此前，我们已完成技术文档的 AI 亲和研究，重点聚焦于正文的可读性与可引用性，并实现了文档站双轨交付（HTML / Markdown / 索引体系）。本次研究则将视野从「说明书如何被 Agent 调用」上移至官网与社区入口层，核心命题转变为：整站在哪些面上需做亲和、索引与交付各自应达到何种深度。

研究旨在回答以下三个关键问题：

  1. 按运营域划分，哪些环节应做亲和改造，哪些暂不介入；
  2. 以「可达性·索引 × 可读取性·交付」为度量维度，刻画各模块的改造程度与优先级；
  3. 从 Mintlify 与 NVIDIA 的实践对比中，抽象出一套可迁移至昇腾社区的设计原则，特别覆盖 Sitemap 发现机制、locale 与子域错位等官网特有的结构性难题。

此轮研究不重复文档层已有成果，而是在入口与导航层建立新的亲和基线，为后续全站 AI 友好度演进提供决策依据。

双轴模型

背书闸门

G · 敢不敢背书

你愿不愿意让 AI 把这页当官方事实原样引用？不愿意就停在基线，业务价值再高也不升档。 它不归属任何一根轴，是一票否决：定价页价值高、内容也独家，却因为报价会变而故意不进目录。

可达性·索引

R = Reachability（可达性）。机器能不能找到这一页。归属：站点配置、索引运营。

  • R0未进索引

    Sitemap 与 llms.txt 两处都搜不到，AI 只能靠外链偶然撞见。

  • R1Sitemap 可发现

    URL 稳定，并进入该内容面对应的 sitemap（文档站用 docs sitemap，不必强行进 www 根 sitemap）。

    报表列 · 收录Sitemap
  • R2llms 目录收录

    写入机器目录（llms.txt 或等价知识索引），让 Agent 一次拿到可引用全集。

    报表列 · 收录llms.txt

可读取性·交付

D = Delivery（交付）。找到之后能不能干净地读走。归属：前端架构、内容生产。

  • D0正文不可读

    正文靠 JS 才出现，且没有平行 MD——拿到 URL 也读不到东西。

  • D1HTML 可读

    不执行 JS 时，HTML 里已有完整主信息（正文、步骤、参数；侧栏、弹层、推荐位不计）。

    报表列 · HTML主信息
  • D2MD 可托管

    平行 Markdown（或等价结构化正文）与 HTML 同源同步；且对 Agent 实际爬取的 locale / 子域可用——不是只在别的地区版有。

    报表列 · MD文件

知识面目标

R1·D1 必达 · R2·D2 加码

文档 / API / 教程 / 支持库。先保证进 sitemap、正文在 HTML 里；再补机器目录与平行 MD。

非知识面默认

R1·D1 封顶

营销、生态、博客、定价、活动、招聘等。Sitemap 可服务 SEO；不进 llms，不强制 MD。

可直接搬的决策

从 Mintlify / NVIDIA 对标沉淀的操作手册：先过三步决策，再对照可搬走结论与明确不做。域定档见下方矩阵。

三步决策

  1. 这页公开吗？是 → R0·D1（主信息进 HTML）。网页基本功，同时服务人、SEO 与爬虫。
  2. 用户会拿它问「怎么做 / 是什么」吗？会 → R1（进对应内容面 sitemap）。多数知识页停这里已够用；子域知识用各站自有 sitemap，不用 www 一票否决。
  3. 长期稳定、愿意背书吗？是 → 再补 D2 平行 MD 与 R2 写入目录。前两步过了这一步仍可能不过——定价页就是；汇总壳页也不必强当知识正文。

可搬走的结论

  1. 管道能力必须学——分区 sitemap、locale 权威 MD、枢纽 llms；大站没有这些，Agent 会系统性迷路。
  2. 全面覆盖必须警惕——防止发布流水线默认全开，把叙事页也卷进 Agent 知识层。工程学 NVIDIA，收口学 Mintlify。
  3. 策展以场景为准——先问愿不愿意背书；严守「事实」与「壳」的界线，再决定是否上 R2·D2。可达 ≠ 该被引用。
  4. 叶子重于汇总——具体可引用页优先；On-Demand 等根页最多做入口指针，不必强做平行 MD 正文。
  5. 分流是为了场景边界——不是刷亲和指标；目标是分面管道 + 窄目录背书，而非全站镜像流水线。

四种明确不做

  • 会频繁变且过期有害定价、活动日程、报价
  • 说服性而非事实性营销卖点、客户证言、博客观点
  • 与产品使用无关招聘、法务、公司新闻、登录账户
  • 壳页与弱背书转化入口、纯导航目录根、社区 / Wiki / UGC

落地顺序

矩阵定「改到哪」，但七个域一起摆在面前时还要回答「先做谁」。按三问推进，顺序不能颠倒。

  1. 过得了背书闸门吗？

    就是上面的背书闸门。不愿意让 AI 把这段内容当官方事实原样引用，就停在基线，业务价值再高也不升档。一票否决，不参与打分。

    定价页价值高、内容独家，但模型引旧价是商业风险——故意不进目录。

  2. 两根轴各到哪一档？

    查上面的决策矩阵，索引与交付分开定档。索引缺口归站点配置，交付缺口归前端与内容生产，别压成同一个待办。

    正文写得够好却没进 sitemap，和进了 sitemap 但正文全靠 JS 渲染，是两种完全不同的问题。

  3. 先做谁？

    只在「必改」范围内用下表打分排序。同样是缺口，先补配置类——便宜、立刻见效；重写正文放在后面。

    补一条 sitemap 记录几分钟就能兑现，重写一个栏目的正文要排几个季度。

排序维度 3 分 2 分 1 分 这项决定什么
业务价值 用户据此做技术选型或实际操作：API、参数、报错处理 辅助理解与选型：方案说明、白皮书 品牌与通识介绍 值不值得排在前面。
内容稳定性 半年以上不大改 有版本节奏，变化可预期 频繁变动，或即将重写下架 要不要上平行 Markdown。同步成本按年计，周更页面做 MD 是负资产。
修复成本 补一条 sitemap 记录或一行目录条目 调渲染方式或页面模板 需要重写正文结构 同等收益下先做便宜的。

打分只排序，不决定改不改。 「改不改」由第一问的风险闸门和运营域判定决定。若把价值与潜力加总来判断是否改造，定价页这类「高价值 + 高独特性 + 高风险」的内容会被算成最该深度改造的一档，结论正好反了。

robots.txt 不是档位。 「不做亲和」= 停在 R1·D1，仍进 sitemap 服务 SEO，只是不进机器目录、不出平行 MD。把不做亲和等同于屏蔽爬虫，会连带杀掉招聘、新闻等页面的搜索曝光，并让 AI 转去引用第三方口径——负收益。

按季度复检。 亲和度会腐化：Markdown 与 HTML 漂移、新页漏进 sitemap、locale 之间不再对齐。新增与改版页面需要重新定档，不是一次性项目。
