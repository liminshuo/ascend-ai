1 发现层部署 — "机器可读版本"入口：
增加固定入口，文案明确为"机器可读版本（source HTML）"或类似表述，禁止用泛化图标替代文字链接。
入口样式规范：
该入口视觉权重与页脚其他导航链接一致，不突出也不隐藏，全站样式统一		 部署 /llms.txt：
按产品线-版本分组，构建管道从 CMS 文档元数据自动生成，文档发布时自动更新，不依赖人工维护。
部署 /llms-full.txt：
构建管道从 /doc_center/source/ 自动聚合所有索引文档的 Markdown 全文为单文件，随文档发布自动重新生成。
<head> 中注入机器发现标签：
每个页面自动输出 <link rel="llms" href="/llms.txt"> 和 <link rel="alternate" type="text/markdown" href="对应source路径">，由页面模板统一生成
sitemap.xml 优先收录 source 路径：
/doc_center/source/ 下的机器源路径优先级（priority）高于渲染页，lastmod 字段从文档 dateModified 自动同步。

放行 source/ 路径，禁止爬取 /assets/、/api/，文件末尾指向 sitemap.xml，引导爬虫走机器源路径。		 实测诊断阳狮团队已识别 Barnett FP1

2 HTML可读 文档内容必须确保传统的搜索引擎爬虫和AI爬虫能够通过静态HTML或服务端渲染（SSR）的方式获取到完整的、不依赖客户端执行JavaScript的内容。具体禁止：无限滚动、动态渲染（页面主要内容不能完全依赖JavaScript客户端渲染）、虚拟滚动、关键内容的懒加载。 禁止设计无限滚动交互：
文档页面不使用无限滚动加载更多内容的设计模式，内容分页或一次性完整展示		 SSR 完整输出页面主体内容：
所有文档正文、标题、代码块、表格必须在服务端渲染到首屏 HTML，禁止依赖客户端 JS 渲染主体内容；
禁止关键内容懒加载：
图片懒加载可以保留，但文字内容（正文、步骤、警示块、验证区块）禁止懒加载，必须随页面 HTML 直接输出；
禁止虚拟滚动：
长列表、长表格禁止使用虚拟滚动组件，必须完整输出所有行的 DOM 节点。
爬虫可达性验证：
在 CI/CD 流程中加入静态 HTML 完整性检测，禁用 JS 后抓取页面，对比关键内容节点是否完整存在，不完整则阻断发布		 实测诊断阳狮团队已识别 Barnett FP1
3 多语言与本地化锚点 如果文档站支持多语言，则必须：
a.hreflang关联
在每个页面的<head>中，必须为每个语言版本包含一个<Link rel="alternate"hreflang="x" href="url"标签，还需要一个 hreflang="x-default"指向默认语言版本;
b.术语翻译一致性；
核心术语在不同语言版本中的翻译必须保持问题和对应。应维护多语言术语表。
c.canonical 标签
每个页面的 canonical 标签应指向其自身。不同语言版本被视为不同页面，各自有自己的 Canonical		 — hreflang 标签自动生成：
页面模板在 <head> 中自动为所有语言版本输出 <link rel="alternate" hreflang="x"> 标签，包含 hreflang="x-default" 指向默认语言版本，由系统根据站点语言配置动态生成，不依赖人工维护。
canonical 标签各自指向自身：
每个语言版本页面的 canonical 标签指向本页 URL，禁止所有语言版本的 canonical 统一指向默认语言版本
多语言术语表数据化：
在术语表原则已有的 Glossary 数据结构基础上，为每个术语增加多语言字段，确保同一术语在各语言版本中的翻译唯一对应，术语一致性检测覆盖多语言场景。		 — Schema.org

4 单文档结构感知 文档的版式和间距必须通过CSS（层叠样式表）控制。禁止使用产生可见空白但无语义的HTML元素来“推动”布局，例如：多个连续的<br>(换行)、空的<p>段落、（不换行空格）堆叠、或用于布局的表格。内容结构应仅由标题<h1>-<h6>、区块(<div>、<sedtion>)、列表（<ul>/<ol>）和段落（<p>）的语义嵌套表达，其间距由全局样式统一决定。 — Lint 规则拦截违规元素：
在构建流程或 CMS 提交环节，检测连续 <br>、空 <p>、 堆叠、布局用表格等违规写法，发布前强制拦截。		 — Barnett FP6
5 失效状态显化 失效状态显性化。版本、上线、废弃、灰度、兼容边界明确写明，AI自动过滤失效内容；已废弃章节在页顶展示弃用提示，并链接代替文档。
a.功能/接口失效
任何已弃用、将下线、或对特定环境无效的功能、API端点、配置参数、必须在描述它的最靠近的标题下方使用显著的警告块进行标记。该警告必须说明：弃用/失效的时间点（或版本）、影响范围、以及代替方案（链接到新文档）。
b.文档失效
对于已停止维护的文档版本或章节，必须在页面顶部（H1上方）展示一个清晰的提示框，说明“此文档适用于已停止维护的[产品名]vX.Y”，并提供一个指向最新版本推荐文档的醒目链接。		 警告块组件规范：
功能/接口失效的警告块需要有统一的视觉样式（颜色、图标、边框），与普通提示框、信息框明确区分，视觉权重足够高，用户不会忽略；
页顶文档失效提示框：
位置固定在 H1 上方，样式与正文完全隔离（如全宽背景色条），包含失效说明文本和指向新文档的醒目链接，不能被页面其他内容淹没。		 失效状态元数据字段：
CMS 中为每个页面和内容块增加结构化字段，包括 status（active / deprecated / sunset）、deprecated-since（版本或时间）、replacement-url（替代文档链接），与内容分离管理，不依赖人工在正文中手写；
失效内容的机器可读标注：
废弃警告块加 data-status="deprecated"、data-since="vX.Y"、data-replacement="url" 属性，大模型抓取时可直接识别该内容块的有效性，自动过滤或降权失效内容；
页顶提示框自动渲染：
当页面 status 字段为 deprecated 时，由模板自动在 H1 上方注入提示框，不依赖内容侧手动添加，避免遗漏；
失效内容在大纲接口中标注：
上文已有页面大纲接口，此处需在接口中为每个内容块带上 status 字段，供大模型在消费大纲时直接过滤失效章节，无需进入页面逐一判断。		 实测诊断 Barnett FP6
6 版本外显 每个文档页面必须在其元数据区域以结构化（机器可优先读）和自然语言（人类可读）两种形式，明确声明：产品/项目名称、文档对应的软件版本号（遵循SemVer）、该版本的发布日期、该版本的生命周期状态（如当前稳定版、维护中、已启用、EOS）、（可选）文档版本自身的版本号。所有版本差异必须使用表格进行条目化描述，禁止使用模糊散文。 版本元数据展示，不使用JS动态渲染：
在页面固定位置（参考 NV 放顶部导航栏或 H1 下方）展示产品名、版本号、发布日期、生命周期状态，位置全站统一。
生命周期状态标签：
稳定版、维护中、已弃用、EOS 用不同颜色的标签组件区分，与失效状态原则的警告色保持一致的色彩语义体系，不能各自定义颜色
版本差异表格样式（可选）：
版本对比内容必须用表格呈现，表格列头（版本号、差异项、说明）样式清晰，设计上禁止用列表或段落替代表格来呈现版本差异		 版本元数据结构化字段：
CMS 中为每个页面增加强制填写的结构化字段：product-name、software-version（SemVer 格式校验）、release-date、lifecycle-status，发布时校验必填，缺失则阻断。
元数据机器可读输出：
版本信息同步写入页面 <head> 的 <meta> 标签和 JSON-LD，如 softwareVersion、datePublished、releaseNotes 字段，供大模型直接读取，不依赖解析页面正文；
SemVer 格式校验：
CMS 在版本号字段录入时强制校验 SemVer 格式（X.Y.Z），拒绝模糊写法如"最新版"、"V2"；
版本元数据在大纲接口中透传：
页面大纲接口返回结果中包含版本元数据字段，大模型消费接口时可直接获取版本上下文，无需进入页面解析。		 实测诊断 Barnett FP6
7 明确更新日期 每个文档页面必须在页面的显著位置（通常在标题下方或者页面底部）以明确的格式标注该页面内容的最后实质性修改日期。日期应遵循ISO 8601 格式（YYYY-MM-DD）以便于机器解析，同时也可以展示为人类友好的格式。仅标注“发布于”初始日期二不持续更新“最后修改”是不够的。 — 使用语义化 <time> 标签：
日期必须用 <time datetime="2026-05-27"> 输出，而非纯文本，大模型和搜索引擎可直接解析 datetime 属性拿到标准格式日期；
last-modified 写入 meta：
在 <head> 中输出 <meta name="last-modified" content="2026-05-27">，以及 JSON-LD 中的 dateModified 字段，机器可读优先保证；
CMS 自动更新日期：
内容发生实质性修改并发布时，由系统自动更新 last-modified 字段，禁止人工维护，避免遗漏或造假；
区分"发布日期"与"修改日期"：
CMS 中两个字段分开存储，datePublished 和 dateModified 独立维护，接口和 meta 中都分别输出，不能合并成一个字段。		 — Barnett FP6

10 内容可追溯性 文档所有内容变更都有明确的追溯记录，包括变更时间、变更人、变更内容、变更原因，核心内容的来源有明确的标注，可追溯到原始来源。 — CMS 版本控制：
每次内容发布自动记录变更时间、变更人、变更内容的 diff，支持回溯任意历史版本，不依赖人工填写变更日志。
变更原因字段：
CMS 发布流程中增加必填的变更原因字段，发布时强制填写，与 diff 记录绑定存储。
内容来源标注字段：
CMS 中为内容块提供可选的来源字段（原始文档链接、规范标准编号、代码仓库 PR 链接等），渲染时可选择是否对用户展示。

页面级变更记录通过接口对外暴露，供大模型判断内容的时效性和权威性，与"明确更新日期"原则的 dateModified 字段联动。		 行业标准 Barnett FP6

11 段落锚点 采用稳定、规范、权威的定义，为AI提供可靠的锚点；各章节具备可引用的锚点ID(如#step2) 锚点跳转的视觉反馈：
用户或大模型通过锚点链接跳转后，目标段落需要有高亮或滚动定位的视觉提示，让用户确认落点正确，避免跳转后找不到对应内容；
锚点链接入口：
每个标题或内容块旁提供可点击的锚点图标（如 # 符号），hover 时显示，方便用户复制引用链接		 锚点 ID 的稳定性保证：
锚点 ID 必须基于内容语义生成（如标题文本的 slug），而非基于渲染顺序或随机值。内容未变动时 ID 不变，避免大模型缓存的引用链接失效；
锚点 ID 覆盖粒度：
不能只有页面级 URL，H1-H5 标题、关键段落、列表块、表格、图片都需要有锚点 ID，保证大模型可以精确引用到内容块而非只能指向整页；
锚点在 SSR 首屏 HTML 直出：
id 属性必须在服务端渲染时写入 DOM，不能由客户端 JS 动态生成，否则爬虫拿不到锚点信息；
锚点与页面大纲接口联动：
“标题明确”原则已有大纲接口，此处需将锚点 ID 作为必要字段输出，供大模型直接获取可引用的精确地址。		 — Barnett FP3
12 步骤列表化 任何描述一系列有序操作（教程、故障排查步骤、安装流程）的内容，必须使用有序列表（HTML<ol><li>.Markdown 1.)进行呈现。每个列表项应包含一个完整的、可执行的行动。禁止使用无编号的段落序列、项目符号列表（无序）或散文段落来模拟操作顺序。 — Lint 检测违规模式：
在发布流程中识别"连续段落以数字+句号开头"或"无序列表内容语义为操作步骤"的违规写法，给出告警；
JSON-LD 映射为 HowToStep：
有序列表在步骤模式下自动输出 HowToStep 结构化数据，每个 <li> 对应一个 step，供大模型精确识别操作顺序。		 — Barnett FP4
Schema.org
13 验证区块 任何描述操作任务（教程、操作指南、配置步骤）的文档，在完成所有操作步骤后，必须显示包含一个名为“验证”或“预期结果”的章节。该章节应提供具体、可执行、可自动化的验证方法，以及明确的成功/失败判断标准。 验证区块独立组件样式：
与前提条件、步骤等模式组件保持同一套视觉体系，但需有自己的标识（如绿色左侧边线或"✓"图标），让用户扫描页面时能快速定位验证区块。
成功/失败状态的视觉区分：
验证区块内的成功判断标准和失败判断标准，用不同颜色或图标明确区分，不能混排在同一段落里。		 验证区块语义标注：
容器加 data-pattern="verification" 属性，成功标准和失败标准分别加 data-result="success" / data-result="failure"，大模型可直接识别验证逻辑，无需推断；
CMS 强制验证区块：
当文档类型被标注为"操作任务"（教程、操作指南、配置步骤）时，发布前校验页面中是否存在验证区块，缺失则阻断发布；
验证方法的代码块支持：
验证区块内的命令或脚本必须用代码块组件输出，带语言标注和一键复制功能，支持可自动化执行的验证命令直接被工具链消费。		 — Barnett FP4
14 图文图意 架构图、流程图、时序图、界面截图关键信息、核心结论采用文本介绍，图片做辅助展示。
a.代替文本
每一张图（<img>）必须提供非空的alt属性。alt文本应简洁描述图片的内容和功能
b.禁止“见上图/下图”
正文中禁止出现“见上图/下图”等仅依赖视觉位置进行引用的语句。图片引用必须将图片中的关键信息用文字复述一遍
c.复杂图表转写
对于包含复杂逻辑的图表，必须在图片下方提供一个“图表内容转写”段落，用文字完整描述图表所表达的全部关键信息。
d.替代格式优先
对于流程图、时序图、架构图，优先使用Mermaid 等文本可渲染的图表格式代替不可读的PNG/JPG图片
e.装饰图片
纯装饰性的图标、分割线图片等，应使用CSS背景图或标记 alt=“”（空字符串）		 图表格式规范：
所有流程图、时序图、架构图，在交付给研发时优先提供 Mermaid 源码，而不是导出 PNG/JPG。如果 Mermaid 表达不了，提供 SVG 源文件。
图片排版预留 figcaption 位：
每张图片下方在设计稿中预留 figcaption 注释区域，作为内容转写的展示位，纳入排版规范，不能设计成没有这个位置的图文布局。
复制链接按钮设计：
在 figcaption 段落旁设计"复制链接"按钮，以及点击后的 toast 轻提示样式（文案如"已复制链接"，持续约 2 秒后消失）。这个按钮需要出现在每个 figcaption 区域。
使用装饰性图片识别：
在设计交付标注中，明确标出哪些图片是装饰性的（图标、分割线等），告知研发这些元素标记 aria-hidden="true" 或使用 CSS 背景图实现，不需要 alt 文字。		 HTML 结构实现：

29 内容结构模式 文档主体内容应遵循一组有限的、可预测的结构模式（Patterns）,而不是自由文本。每个模式有固定的章节名称、顺序和内部格式。至少应包含以下模式中的大部分：前提条件、步骤（有序列表）、验证（预期结果）、示例（代码块）、定义列表、故障排除（表格/列表）。模式之间用二级或三级标题清晰分隔。 每种模式对应独立组件样式：
