SITEMAP OPTIMIZE · DRAFT · 2026-11-18

昇腾社区 Sitemap 优化建议

基于现网 11 份 Sitemap 导出复核：按「先语义、后容量」重组分册，使 Agent / 爬虫可按栏目选开，而不必遍历编号混装分片。本页给出归类规则、建议文件名，以及按规则组装后的根索引。

去重约 76,758 URL现网 11 分片建议：语义分册 + sitemapindex
11现网分片数
76,758去重后 URL
60,560文档详情占比
1建议 robots 只声明根索引
01

现网怎么分的

现状是生产切片（data / doc + 序号），不是按 document / developer 业务频道语义分册。
现网文件实际内容切分方式
sitemap-zh-CN.xml / sitemap-en-GB.xml语言站少量入口按语言
sitemap.xml主站杂项入口小清单
sitemapdata1/2.xmlforum / developer 博客活动 / 案例库等混装混装后按容量切 2 片
sitemapdoc1…6.xml几乎全是 /document/detail/…约 1 万条/片溢出切片

在 sitemapdoc* 里看到的 “developer”，多为文档路径中的 developer_guide 字样，不是开发者频道 /developer。

Agent 读这个 Sitemap 的问题

  1. 无法按意图选开文件。robots.txt 平铺声明多份 Sitemap，文件名又是 sitemapdata1 / sitemapdoc1 这类编号。Agent 若要找开发者、学习或某类文档，无法从名字判断该先读哪一份。
  2. 只好多文件遍历。没有语义分册时，只能把 11 份清单依次打开再过滤 URL；单份常接近 1 万条，token 与往返成本高，还容易在中途截断后漏掉目标页。
  3. 混装放大误选。sitemapdata* 把论坛、博客、活动与开发者页混在一起；sitemapdoc* 又按容量切文档池。Agent 即使打开了“看起来相关”的分片，仍可能扫到大量无关条目，定位效率低。
02

归类规则

  1. 先按 Host：非 www.hiascend.com 不进主站 Sitemap（现约 483 条，单独治理/剔除）。
  2. 再按路径一级语义（下表，按匹配顺序）。
  3. 超限再二次拆分：单文件建议仍按约 1 万条封顶；文档按 /document/detail/{lang}/{产品}/ 的产品名拆，单产品仍超限则加 -01 -02…

05

预期收益与边界

能改善不宜过度承诺
Agent / 运维可按栏目选开 1 个分册，不必先遍历 11 个混装编号文件；根索引收口降低 robots 漏声明风险；与 llms 分层治理语言对齐。 仅改文件名不会自动拉高收录率，也难单独压掉重复 URL / 异常 Host / 查询参数膨胀。维度 1 硬指标仍需去重与条目清洗。
建议实施顺序：① 去重 + 清异常 Host/查询参 → ② 按本规则语义化命名并改为 sitemapindex → ③ robots 收敛为单行根索引声明。
证据：Ascend C 的基础设施/sitemap/*.rtf · 与基线 77,430 / 76,753 同源复核 · 2026-11-18
