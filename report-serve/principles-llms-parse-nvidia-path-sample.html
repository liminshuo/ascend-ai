建立可发现的入口路径：
找的到、路径通畅明确

人能打开官网页面，不代表模型能找到。若入口不稳或许可声明挡路，页面在检索阶段就进不了候选池。

本原则要求官网页面对模型可发现、可进入。

  1. G1.1. robots 许可声明，放行 Agent 抓取
  2. G1.2. llms.txt 索引，覆盖需背书的知识面
  3. G1.3. sitemap 清单，条目语义化
  4. G1.4. 节级锚点，按段读取不必整篇扫

robots.txt

根路径的许可声明，用来划定知识面抓取边界：放行该抓的，拦截不该抓的。没有强制准入力，部分 Agent（如 GPTBot）根本不请求。

遵循 RFC 9309：遵守该协议的爬虫进站直接请求根路径 /robots.txt，路径由协议固定，不靠站内链接或搜索。

  1. 1. 逐层进入

    先从根 llms.txt 进入，再按站点、产品逐层进入分册，最后打开具体 .md。

  2. 2. 整篇拿全

    读取时，一篇要一次拿全，不跳段、不截断。

  3. 3. 索引跳读

    在索引中跳读——只看模块标题和标题描述，对上的相关内容整段读取。

  4. 4. 循环补齐

    若回答不完整，回到 llms 索引找下一篇 .md，直到能完整回答为止。

打开后 · 节级锚点

Agent 打开正文后，节级地址让引用落到哪一篇的哪一节，不必把整页当一条证据。

  1. 1页地址告诉 Agent 引用知识来自于哪篇文章。
  2. 2节锚点# Package Manager Installation 与节名③同名，告诉 Agent 引用知识来自于哪个段落。
  3. 3节名人看见的节标题，在正文里「4. Package Manager Installation」左侧。
  4. 4「复制点 #」是把带锚点的完整节地址交出去：把这条贴进对话，下一轮 Agent 才能从这一节起读，而不必从页顶再扫。「已复制链接」只告诉人：节地址已经进剪贴板。

Provide a machine-readable
body the model can parse

提供机器可读的正文形式：
读的懂、内容完整可读

人读页上信息看起来完整，但 Agent 只消费能解析的正文。图、链接、折叠内容如果没有写进 HTML，响应体里就只剩骨架，模型拿不到完整内容。

本原则要求所有事实内容以机器可读的形式完整给出。

  1. G2.1. 第一次 GET 即含正文，不依赖 JS 填充
  2. G2.2. 人读页与 Markdown 同源
  3. G2.3. 信息载体语义化，图、链接、颜色、图标明确
  4. G2.4. 隐藏交互信息可抓取

Agent 工作流

代码块可验证

执行类代码须标明语言、正文不含行号，并提供预期输出，以便识别、复制与核对。

  1. 1语言类型标明代码语言，供人与 Agent 识别。
  2. 2操作提供复制，及「咨询智慧助手」以针对该段代码提问。
  3. 3预期输出给出执行成功后的可见结果，供核对。
  4. 4代码行行号写进代码正文，复制与入库被污染。
常见问题
  • 代码块顶未标明语言，Agent 查询语言耗费 token
  • 代码行有数字标记，导致代码抓取混乱

历史素材

根 llms

  1. 1集团名用 # 写集团叫什么。
  2. 2集团说明用 > 交代这份清单是什么、下一步跟哪。
  3. 3站点名用 ## 按站点切块，先扫站名再进节。
  4. 4站点 llms 分册地址写成 - [标题](地址): 说明。本行链到下一本清单，不是正文。

文档站 llms 分册

  1. 1站点分册名用 # 写这份文档分册叫什么。
  2. 2站点分册说明用 > 说明这是各产品 llms.txt 的总册。
  3. 3产品名用 ## 按产品线切块，先扫产品名再进节。
  4. 4产品说明用 > 写这一条产品线是什么。
  5. 5产品 llms 分册地址写成 - [标题](地址)。本行链到 CUDA 产品册，下一跳还是清单。

文档站下 CUDA 的 llms 分册

  1. 1产品分册名称用 # 写本产品分册叫什么。
  2. 2产品分册说明交代这本产品分册覆盖哪些任务。
  3. 3节名用 ## 按任务切块，先扫节名再进节。
  4. 4文章写成 - [文章名称](文章地址)，地址以 .md 结尾，下一跳才是正文。本例是 Linux 安装页。
