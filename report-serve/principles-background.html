设计背景

面向设计、文档内容与前端同事：先讲清现状与场景，再说为何要立原则、它与 GEO / RAG 的关系、能带来什么价值，以及如何复用到其他业务线。改造细则见 AI 亲和原则 与 全量亲和原则。

1. 背景与现状

越来越多的人获取产品与技术知识时，会先问大模型，而不是打开官网、在手册树里逐级点开。提问场景很具体：怎么装、版本差在哪、规格能不能用、报错怎么排。他们期望得到可执行的官方答案，而不是营销话术或过时片段。

大模型给出的答案，很大程度上取决于公开面上的文档站、手册与规格页能不能被机器稳定发现、完整读取、正确理解。若页面「人看着有内容」，但机器抓不到正文、进不了章节、分不清版本，模型就会用训练记忆补洞——表现为幻觉、答非所问、或把旧版当现行。

这不是个例风险，而是知识交付入口正在从「人浏览官网」切到「人问模型、模型读官网」时的结构性变化。官网与文档仍是权威来源，但消费路径变了：第一读者里多了一类「机器读者」。

2. 为什么要做 AI 亲和原则

如果我们只按给人看的版式改文档，机器侧的断点会系统性漏掉：发现层未部署、入口只靠图标、正文依赖客户端渲染、图意无字、折叠默认不输出、版本与邻篇对不上号……任何一环失败，都会在答问链路里放大成错误指引。

因此需要一套跨角色共用的原则：把「机器能不能用这份文档」拆成可验收的目标，让设计、内容、前端在同一标准下分工改造，而不是各自凭经验补丁。

  • 对设计：入口、信息层级、默认可读态要可被发现与跟链，而不仅是视觉好看。
  • 对内容：命名、版本、步骤、预期结果要可独立理解，机器和人读到的是同一套事实。
  • 对前端：首包可得、锚点稳定、发现层与平行源可部署，管道能自动校验，而不是上线后再人工补洞。

AI 亲和原则据此将答问链路整理为可达 → 可读 → 可理解 → 可操作 → 可验证五层，并落到设计 UI / 文档内容 / 前端三交付面，作为统一对照标准。

3. 与 GEO、RAG 的关系

讨论「文档适不适合被 AI 用」时，常会听到 GEO、RAG。它们和本原则不在同一层，需要先分清：

名称 是什么 关心什么
RAG 技术架构：先检索文档再生成回答。 文档能否入库、切块、召回、进入模型上下文。
GEO 优化目标：让内容更容易被生成式引擎选中并引用（类比 SEO）。 权威页能否进候选池、是否值得被当成答案来源。
AI 亲和原则 改造做法：文档与官网公开面如何改，机器才找得到、读得懂、用得上。 设计 / 内容 / 前端各自交付什么、如何验收。

一句话：RAG 是用法，GEO 是战场目标，AI 亲和原则是文档侧要满足的条件——同时服务「知识入库」与「生成式引用」，而不是其中某一项的别名。

4. 原则的价值

把原则落地后，价值不在「多写几份规范」，而在答问质量与协作效率：

  • 降低错误答案：官方事实页更稳定进入候选与引用，减少幻觉、过时版本与壳页被当成权威。
  • 缩短改造沟通：设计、内容、前端共用同一套「可达～可验证」语言，验收有条目可对，少靠口头经验。
  • 一次改造、双轨受益：人读体验与机器消费同源推进；发现层、平行 MD、正文可读性同步达标，避免给人一套、给机器另一套。
  • 可度量、可迭代：全量表与问题实测把原则拆成可勾选状态，便于排期、回归与跨站对照。

5. 如何复用到其他业务

五层目标（可达 / 可读 / 可理解 / 可操作 / 可验证）描述的是机器消费公开知识的共性能力，不绑定单一产品线。社区文档站可以落地，能源、云、终端、开发者门户等同样适用——换的是业务事实与页面载体，不变的是链路与验收逻辑。

跨业务复用时，建议保持框架，替换内容：

  • 保留：五层目标、三交付面、发现层 / 双轨 / 入口可辨识等共性要求。
  • 替换：产品名、版本体系、规格字段、操作步骤与验证方式等业务事实。
  • 划界：营销活动页、登录墙、临时域名等，在收录策略里明确是否纳入完整改造。
  • 起步顺序：先定「应被引用的官方事实面」→ 跑通可达与可读 → 再补可理解 / 可操作 / 可验证。

因此本原则既是当前社区文档与官网的改造标准，也可作为其他业务线做「AI 可读官方知识面」时的共用方法论：先对齐框架，再填入本域内容。
