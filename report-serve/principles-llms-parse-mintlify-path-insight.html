洞察

先分清两件事

Agent 读文档，不是在浏览器里滚动。它对某个 URL 做一次 GET，这一份文件全文回来，然后在这份文字里决定要不要再 GET 下一个地址。

GET 是取文件：一次请求，整份 llms.txt 或整份 .md 都回来，没有「只下载第 3 节」。读 是回来之后怎么用这些字：顺读、只扫节名、某几条看都不看。绿行 / 没涂色画的是读，不是 HTTP。

所以效率主要不在「同一份里少读两行」，而在 少打开下一份 URL，以及已经打开过的目录 不要当新文件再扫一遍。

对照哪两条路径

下面六条都从 Mintlify 两条实测路径里来。编辑器快捷键是单任务：根清单 → 文档分册 → 181 页总表 → 快捷键正文，打开 4 份文件，Related topics 不再打开。CI 部署排障是两个任务拼在一起（REST 触发部署 + OpenAPI 拉取失败）：根清单 → 文档分册，分册里已经有 API 页和 Help 页的直链，所以不进 181 页；先打开 Trigger，发现排障不在这页，再打开 Help。

1 · 有直链就不要进 181 页总表

分册 docs/llms.txt 里其实有两种目录。一种是任务直链：## API reference、## Help center 下面直接是某一页的 .md。一种是页名总表：页顶那条 Documentation（181 pages），点开是 181 个页名排在一起。

快捷键在分册里没有单独一节叫「编辑器快捷键」，所以只好进 181 页里搜，多了一次整文件 GET。CI 的 Trigger 和 OpenAPI 排障已经写在分册里，再进 181 页就是浪费。

Agent 可以定一条硬规则：当前这份清单里已经出现「能回答问句的那一页的链接」，就跟它；不要为了「更全」再打开总表。

原则高频、能独立成答的任务页，在分册里直链 .md。页名总表只外包扫不完的页，不是必经层。能直链的不要只藏在 181 页里。

2 · 问句先拆成几个任务面，再决定跟几条

快捷键是一件事，每一层只跟一条，跟到正文就停。CI 是两件事：怎么用 REST 触发部署，以及构建报 Failed to fetch OpenAPI 怎么排。两件事不在同一页，但都在同一本分册里。

高效顺序是：第一次扫分册时两条都记下（还没打开）；先 GET Trigger；读完发现还缺排障，再 GET Help。不要一看到两条就同时打开两页，上下文会立刻胀一倍；也不要先去 181 页里撞。

「记下」只是记住 URL；「打开」才是下一次 HTTP。打开是先后的，不是两页同时 GET。

原则问句若跨两个任务，分册里应有两个并列的任务节，两条直链都能从同一本够到。两页互相不能替代时，不要指望一篇的 Related topics 顶另一篇。

3 · 回到分册，不等于把分册当没读过

CI 那条第二次给分册标 12，是保守画法：同一份 docs/llms.txt 再 GET 一次，从标题重新扫到 Help。第一次跳读到 ## Help center 时，其实已经见过那条 OpenAPI 链接。

更省的做法：Trigger 读完缺排障，直接 GET 已经记下的 Help URL，不必再把 Admin、Agent、Analytics 节名过一遍。再 GET 叶子该付；再扫一遍目录可省。目录还在这次对话的上下文里，就不要当新文件。

原则分册可能被再 GET、再扫一遍，站点控不了某次会不会重读，但控得了再读的成本：分册尽量短，只当本域目录；按任务分节，节名稳、同构，第二次靠 ## Help 就能落到该进的那一块。又短又糊，重读照样找不到。

4 · 当前页已经能答，就不要再点 Related

两篇正文底部都有 Related topics。若每页再 GET 三个相关页，跳数会爆。打开次数看问句还缺什么，不看这页还链了谁。

快捷键表齐了就停。Trigger 页答了怎么 POST，没答 OpenAPI 失败，才需要再跳——跳的是分册里那条 Help，不是 Related 里随机关联页。这和「目标页一次取完，剩下的在 Agent 自己的环境里想」是同一类停法。

原则叶子页要自足：问句所需写在正文里，页顶就能判断本页答什么、不答什么。Related topics 是人读导航，不当 Agent 的下一跳目录。

5 · 一份文件内部，用节名当过滤器

GET 已经把整份文件带走。所谓跳读，是少把已下载的字拿来推理，避免跟错链。

根清单：读到 Docs 的 Documentation index 就够，定价、博客那些条目不用跟。分册：API 里读完 Admin 整节（才能判断是 Trigger 不是 Get status）；Agent / Analytics 只看 ### 节名，不读每条接口说明。

## / ### 几乎都要扫过（用来排除）。节里的链接只有「像答案」的那一节才逐条看。只有决定跟的那一条才再 GET。

原则节名按任务面来写，不要把站点树原样搬家。同一节里每条说明要能用来排除（Trigger 不是 Get status），否则候选节读完也选不准。

6 · Agent 能省多少，会被目录形状卡住

快捷键必须多一跳，是因为分册没把「键盘快捷键」写成和 API、Help 同级的任务节。Agent 再聪明，分册里找不到，就只能进 181 页。

链接文案若写成「什么时候读这一页」（例如 Linux 安装、thread / block / grid），第一次跳读节名就能点中，不必先打开一本页名总表。

Agent 能做的：有直链就不套总表；跨任务先记账再串行打开；记住的 URL 不要重扫目录；答完就停。站点能做的：按任务分节、链接说明何时读、能直链的不要只藏在 181 页总表里。后者往往比让模型「读得更快」更有效。

原则链接名称用标题，后面一句写清何时读这一页。任务面要升到分册的 ##，升不上去，Agent 只能进页名总表。

从路径推出的原则

  • 每份可 GET 的文件都要能扫完一次请求带走全文，根清单、分册、叶子都一样。答案靠前；扫不完的页名外包，不把正文写进目录。
  • 能直链的任务不要经过页名总表分册里已有 .md 就跟它。181 页总表只给分册塞不下的页，不是每问必经。
  • 跨任务在同一本分册并列直链两页互相不能替代时，都要从这一本够到，不要靠 Related 串起来。
  • 分册按可能被再读来写尽量短，只当本域目录；## 按任务分节、节名稳定。再 GET 一次时，成本可控、靠节名就能落到该进的块。
  • 叶子自足，Related 不当目录页顶写清本页答什么。问句所需写在正文。人读相关页不要当成 Agent 的下一跳清单。
  • 节名可跳读，同节说明可排除节名是任务面。候选所在节的条目要能判断跟谁、不跟谁。
  • 链接写清何时读名称用标题，说明写使用场景。任务升不到分册节级，再聪明也多一跳总表。

收束

  • 下载是整份的，决策是挑着的一次 GET 带走全文；绿行是用来做决定的那些字。没涂色不等于没下载。
  • 能少打开一份文件，就比在一份文件里多读两行更划算贵的是下一跳 URL，不是页内跳读。
  • 跨任务在目录里记账，打开仍串行同一本分册可以记下两条；先打开一条，缺什么再打开第二条。
